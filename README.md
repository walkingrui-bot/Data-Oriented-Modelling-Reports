# Data-Oriented Modelling — Reports

## What Data-Oriented Modelling means

Data-Oriented Modelling starts with a practical idea: **first understand how the world produces your data, then build a model around what you find.** Our studies of language, chemical structure, multiple observers and agent control approach this from different directions. They are converging on the same question: what can we measure about a problem that tells us what kind of model it needs?

Consider a moving object. Record its position once a second and you can follow its path. Average the whole journey into one number and much of that movement disappears. Change the instrument, the sampling interval or the way readings are grouped, and the same world leaves a different set of data. So our first job is to understand the measurement: which differences came from the world, and which came from the way we observed it?

A sentence has word order. A molecule has atoms and bonds. Repeated measurements have a history. Those relationships give us different things to study, and we want to understand what they carry before deciding how to represent them together. The Data Passport design starts by recording what each observation refers to, how and when it was made, where it came from and how uncertain it is. **First find out what each kind of data actually is.**

Time makes the point especially clearly. Imagine six instruments taking readings at the same instant. Hand those six records to a model in a different order, and the underlying moment is still the same. Now take readings as the world changes. Reversing their order changes the story. Think of shuffling photographs of one moment versus playing a film backwards. The Internal Coordination experiments test this distinction directly: same-time observations can be rearranged while the inferred state stays the same; reversing a changing world's timeline makes inference worse. **Presentation order and world chronology have different jobs.**

Once we understand the observations, we can begin with direct statistics. Count the possible combinations. Map which points are neighbours. Measure which relationships survive a change of source or setting. Ten columns may contain ten independent signals, or mostly repeated views of one signal. Finding that out already tells us something about the model we need.

This is where complexity has to earn its place. In the GDI Data Cloud experiments, extra specialist modules carry a computational cost. Persistent patterns in the errors can justify creating a module; modules that receive negligible use can become dormant. Their value is then checked on data left out of fitting. The principle is simple: **complexity is something the data has to ask for.** A memory, an expert or another layer needs a repeatable problem to solve. When a compact model captures the reliable structure, keeping it compact is a research result.

To find where information matters, we make a small change and follow its consequences. In the Multiscale Language experiments, we replace a word with alternatives of a similar type and length, and measure how much that replacement disrupts prediction of the following passage. This gives “importance” a concrete meaning: how much does changing this word affect what comes next? It also gives model design a measurable target—preserve the information whose loss damages the continuation.

The same question travels across the research programme. Change a route inside an agent and follow the rest of the task. Compare a small molecular edit across different examples and measure how the response changes. Add an earlier observation and test how much it improves the next prediction. Direct interventions in a model let us test the contribution of the component we change; matched comparisons in recorded data establish the relationships that need further explanation. In each case, we study a local change together with its consequences.

Then we ask what stays stable. In the Chemical–Odor studies, changing an acid into an ethyl ester often produced a common direction of odor change across the tested examples. That supports a relatively simple shared rule. Adding a CH₂ group behaved differently: a single common direction explained little, while the previous change in response helped predict the direction of the next change along held-out chemical-edit trajectories. Predicting the size of that change remained harder. Here the model's state summarizes where we are along an observed sequence of edits and responses.

This gives us a practical reason to build different kinds of computation. A stable relationship may need only a direct mapping. A relationship that depends on the current situation needs that situation represented. If earlier changes help explain the next one, the model has a reason to retain and update a memory. Sometimes the useful regularity lies in how the rule itself changes. Each of these is a question to test before giving it a place in the architecture.

Several observers bring another challenge. Each may see a different part of the same situation through a different measurement process. We let local models learn their own observations, then ask them to support a shared account of what is happening—one that can explain what the different observers see. In the controlled Internal Coordination experiments, stable differences between channels and temporary changes in a channel receive separate roles. That distinction helps the system work out whether a sensor has drifted or the observed world has changed. The shared structure coordinates models built for the particular data each channel supplies.

For an agent, the account of the world must eventually guide an action. Useful information can be present while the system still selects the wrong operation or acts at the wrong stage. In the controlled routing experiments, locking an old route could leave an immediate answer largely intact while damaging recovery over the rest of the task. Following the whole sequence reveals a job for routing that a single answer score can miss. The agent therefore needs to track what it believes, which actions are currently eligible, what it commits to, what actually happens and how that result changes its state.

By the time we design the architecture, we want a reason for each part: this mapping captures a stable relationship; this memory carries a useful history; this local model handles a distinct observation process; this coordination step reconciles several views of the same world. We test those reasons on new entities, sequences and sources, and use interventions to locate which components do the work.

That is the design philosophy connecting these studies. We investigate the data closely enough to ask: **what kind of computation does this particular world call for?** Then the model can grow out of the experiments. **Model design itself becomes an outcome of data analysis.** Our aim is to make *when to build which model* something we can study experimentally.
